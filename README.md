# FSM DSL and Code Generator for Rust (`.ssot`)

This project provides a Domain Specific Language (DSL) inspired by Cap'n Proto for defining Finite State Machines (FSMs) and tools to generate type-safe **Rust code**, **Cap'n Proto schemas**, and **TypeScript type definitions** from these specifications. The `.ssot` extension signifies the **Single Source of Truth** for the state machine.

## Background

The core idea is to leverage a dedicated DSL (`.ssot`) for declaratively defining FSMs. This approach aims to:

*   **Model Intuitively:** Represent states, events, and transitions clearly.
*   **Generate Multiple Targets:** Automatically generate code and definitions for different platforms and use cases (Rust, Cap'n Proto, TypeScript).
*   **Ensure Type Safety:** Generate artifacts that enforce the state machine rules at compile time (Rust) or provide strong typing (TypeScript, Cap'n Proto).
*   **Centralize Specification:** Use the `.ssot` file as the definitive source for the FSM's logic, from which code, schemas, types, documentation, and potentially other artifacts can be derived.

## Project Goal

The primary goal is to enable developers to define state machine logic declaratively in a `.ssot` file and automatically generate the necessary boilerplate code and definitions for Rust, Cap'n Proto, and TypeScript, ensuring type safety and reducing manual implementation effort across different parts of a system.

## Workspace Structure

This project is organized as a Cargo workspace containing the following crates:

*   `crates/fsm-dsl`: Defines the `.ssot` grammar (`ssot.pest`), the Abstract Syntax Tree (`ast.rs`), and the parser logic (`parser.rs`) using the `pest` library.
*   `crates/fsm-codegen`: Takes the AST generated by `fsm-dsl` and generates corresponding **Rust code** (`lib.rs`), **Cap'n Proto schemas** (`codegen_capnp.rs`), and **TypeScript types** (`codegen_ts.rs`). It utilizes libraries like `syn`, `quote`, and `prettyplease`.

*   `crates/fsm-example`: A demonstration crate showing how to use the DSL. It includes a sample `spec/my_fsm.ssot` file and utilizes a `build.rs` script to invoke the parser and code generators during the build process.

## Usage (Example)

1.  **Define your FSM:** Create or modify a `.ssot` file (e.g., `crates/fsm-example/spec/my_fsm.ssot`).
2.  **Add Annotations:** Specify output directories and add descriptions using annotations within the `.ssot` file:
    ```fsm
    @0x...; // File ID is required

    // Top-level annotations apply to all machines unless overridden
    $rust_out("src/generated");
    $capnp_out("schema/capnp"); // Optional: Generate Cap'n Proto schema
    $ts_out("schema/ts");    // Optional: Generate TypeScript types

    $description("Description for the whole state machine.");
    stateMachine MyMachine {
        // Machine-level annotations override top-level
        // $rust_out("src/another_place");

        states {
            $description("Initial state.");
            Idle @0;
            $description("Active state.");
            Running @1;
        }
        events {
            $description("Event to start.");
            event Start @0 {
                $description("User ID.");
                userId @0 : UInt64;
            }
            $description("Event to stop.");
            event Stop @1;
        }
        // ... transitions ...
    }
    ```
3.  **Build:** Navigate to the workspace root (`ssot/`) and run `cargo build`. This will:
    *   Build `fsm-dsl` and `fsm-codegen`.
    *   Execute the `build.rs` script in crates that use the generator (like `fsm-example`).
    *   The `build.rs` script will:
        *   Parse the `.ssot` file(s).
        *   Call `fsm_codegen::generate_rust_code` and write the result to the path specified by `$rust_out` (e.g., `src/generated/my_machine.rs`).
        *   If `$capnp_out` is present, call `fsm_codegen::generate_capnp_schema` and write to the specified path (e.g., `schema/capnp/MyMachine.capnp`).
        *   If `$ts_out` is present, call `fsm_codegen::generate_typescript_types` and write to the specified path (e.g., `schema/ts/MyMachine.types.ts`).
    *   Compile the crate (e.g., `fsm-example`), linking against the generated Rust code.

*(Note: Examine `fsm-example/build.rs` for the implementation details of the build script logic.)*

## DSL Annotations

*   `@0x...;`: **Required** top-level unique ID for the file (Cap'n Proto compatible).
*   `$rust_out("path/to/dir")`: **Required** (top-level or per-machine). Specifies the output directory for generated Rust code. The filename will be `<MachineNameSnakeCase>.rs`.
*   `$capnp_out("path/to/dir")`: Optional (top-level or per-machine). If present, generates a Cap'n Proto schema file named `<MachineName>.capnp` in the specified directory.
*   `$ts_out("path/to/dir")`: Optional (top-level or per-machine). If present, generates a TypeScript type definition file named `<MachineName>.types.ts` in the specified directory.
*   `$description("...")`: Optional. Can be placed before `stateMachine`, `state`, `event`, or `field` definitions. The string value will be used to generate documentation comments in the output files (Rust `///`, Cap'n Proto `#`, TypeScript `/** ... */`).
*   `$initial(StateName)`: **Required** on `stateMachine`. Specifies the entry state.
*   *(Other annotations like `$version`, `$derive` might be parsed but may not be fully utilized by the code generator yet.)*

## Current Status

*   Parsing of the `.ssot` DSL including states, events (with fields), transitions, and annotations is implemented.
*   Generation of functional Rust code (state enum, event enum/structs, machine struct with `on_event` logic, callbacks trait) is implemented.
*   Generation of Cap'n Proto schemas reflecting the FSM structure (states, events, payloads) is implemented.
*   Generation of TypeScript type definitions (state union, event discriminated union, payload interfaces) is implemented.
*   Documentation generation from `$description` annotations is supported for all three output formats.
*   The `fsm-example` crate demonstrates the build-time code generation workflow for all outputs based on annotations.

## Roadmap / Future Enhancements

*   **Core DSL Enhancements:**
    *   Add syntax for entry/exit actions on states.
    *   Enhance validation rules within the parser (e.g., duplicate name/ordinal checks, transition validity).
    *   Support for more complex annotation values or specific annotations (e.g., `$deprecated`).
    *   Investigate support for hierarchical state machines in the DSL.
    *   Add syntax for defining distributed system components/services and their interactions (potentially referencing external `.ssot` or interface files).
*   **Expanding SSOT Scope (within DSL):**
    *   Integrate routing definition capabilities (e.g., mapping states/events to routes or defining navigation flows).
    *   Specify inter-service communication mechanisms (e.g., RPC, messaging) and link them to FSM events/actions, defaulting to Cap'n Proto for interfaces.
    *   Explore defining related concerns within `.ssot`:
        *   UI/UX Component Mapping (Linking states/events to UI elements/actions).
        *   API Call / Event Integration (Defining external calls or internal events triggered by FSM).
        *   Authorization / Permissions (Specifying required roles/permissions for transitions/events).
        *   Test Scenario / BDD Definitions (Describing test cases or BDD features based on FSM paths).
        *   Monitoring / Logging / Alerting Rules (Defining observability requirements per state/transition).
        *   Configuration Management / Feature Flag Integration (Defining or linking configuration values).
        *   Compliance / Audit Log Requirements (Specifying necessary audit trails).
        *   Formal Verification / Simulation Support (Adding annotations for model checking/simulation).
*   **Core Code Generation Enhancements:**
    *   Generate placeholder or skeleton functions for defined `guard` and `action` attributes **in Rust**.
    *   Improve generation for hierarchical state machines (dependent on DSL enhancement).
    *   Generate Cap'n Proto interface definitions (`.capnp`) specifically for defined inter-service interactions.
    *   Generate Cap'n Proto-based client/server communication stubs in target languages (Rust, TypeScript, etc.) based on defined interactions.
*   **Expanded Code Generation Targets & Formats:**
    *   Explore generating visualization outputs (e.g., Mermaid syntax, Graphviz DOT) from the AST.
    *   Generate advanced documentation (e.g., state tables, sequence diagrams, user guide sections).
    *   Integrate generation capabilities based on various standard formats:
        *   **Requirements:** ReqIF (`.xml`), Markdown/Asciidoc (`.md`, `.adoc`)
        *   **Process/Architecture:** BPMN (`.bpmn`), ArchiMate (`.xml`)
        *   **System Modeling:** UML/SysML (XMI `.xmi`)
        *   **Data/Schema:** JSON Schema (`.json`), XSD (`.xsd`), Avro (`.avsc`), Protocol Buffers (`.proto`)
        *   **API/Interface:** OpenAPI (`.yaml`/`.json`), gRPC (`.proto`), GraphQL SDL (`.graphql`), AsyncAPI (`.yaml`/`.json`)
        *   **Database Schema:** Prisma Schema (`.prisma`), Drizzle ORM (`.ts`), Drizzle Kit Config (`drizzle.config.ts`), SQL (`.sql`), DBML (`.dbml`), Liquibase (`.xml`, `.yaml`, `.json`, `.sql`)
*   **Project-Specific Generation & Integration:**
    *   Generate Next.js routing configurations (e.g., `app/` directory structure, `route.ts` handlers based on FSM states/events).
    *   Generate database migration scripts (e.g., SQL `up`/`down`) based on diffs between `.ssot` file versions.
    *   Implement project-specific code generation orchestration (e.g., specifying `nextjs` target generates relevant Rust, TS, routing, migration scripts, etc.).
    *   Explore generating deployment/orchestration configuration hints (e.g., Docker Compose, Kubernetes manifests) based on the defined distributed system structure.
    *   Add support for generating platform-specific configurations and deployment helpers (e.g., `fly.toml`, `vercel.json`, Supabase functions/config) based on `.ssot` definitions.
*   **Developer Experience & Tooling:**
    *   Improve error messages and diagnostics from the parser and code generator.
    *   Enhance automated tests, particularly for `build.rs` logic (e.g., via integration tests) and edge cases in generation.
    *   Implement the `#[state_machine(...)]` procedural macro approach as an alternative integration method for Rust projects.
